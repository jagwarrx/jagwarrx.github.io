Ask a Better Question

November 2026. 529 words.

When I hit a problem, my first move is to build a tool for it. I’m a software engineer, building is the fun part, and a tool feels like a real answer. Often it isn’t the answer I needed.

The rule I use now is short. Stop and rethink. Ask a better question.

Stop

The moment to stop is the moment I catch myself starting to build. That urge feels like progress, and it skips a step. “How do I build this?” is a question I enjoy, so I jump straight to it. It’s almost never the first question.

The question I ask decides what I do next. Questions come before decisions, and decisions before actions. “How do I build this?” can only end in a build. So the fix isn’t more discipline while building. It’s a different question before I start.

The better question

It has two parts. What am I trying to achieve? And is there an easier, quicker or better way to do it?

The first part moves me from the tool to the result. The tool is never the goal. The goal is a decision made, a thing understood, a task done. Once I name the result, the tool is only one way to get there, and usually the slowest.

The second part has three words in it, and they aren’t the same. Easier means less work for me. Quicker means the answer arrives sooner. Better means closer to what I wanted in the first place. Any one of the three is enough reason not to build yet.

Run it through a prompt first

These days the easier, quicker way is often a prompt. Instead of creating a tool, I take the real thing, the document or the list or the data, paste it into Claude, and ask the question the tool was supposed to answer. It takes minutes.

What I’m checking is whether the idea is relevant at all. There are three ways it can go.

The answer isn’t useful. Then the tool wouldn’t have been either. It would have given me the same answer, later, with a nicer screen. I’ve saved the whole build.

The answer is useful, and I needed it once. Then I’m done. There was never a tool to build, only a question to ask.

The answer is useful, and I’ll need it again and again. Now a tool is worth building. And I’m no longer guessing what it should do, because I’ve seen the output I want. The prompt is the first draft of the tool.

How far this goes

Some things do need building. Anything that has to run many times, run without me, or be used by other people can’t stay a prompt I paste by hand. The rule doesn’t say never build. It says the build comes after the question, and after the cheap test.

Building for fun is fine too, as long as I call it that. The trouble only starts when I build for fun and tell myself it’s the fastest way to the result.

The stop takes a minute. It’s the cheapest step in the whole job, and the easiest one to skip.
