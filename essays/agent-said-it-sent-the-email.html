Your agent will say it sent the email

September 2026. 676 words.

Getting a model to talk is the easy part now. You can have a voice agent holding a decent conversation in an afternoon. The hard part starts when you let it do things: create the lead, change the contract, send the email. Every rule below is in a prompt or a tool I've built.

It will say it did the thing

The first time an agent tells a user "Done, I've sent that over," check whether it called the tool. Often it didn't. The model has read a million conversations where someone says they sent the email, and saying it is the most likely next sentence. Nothing in the language makes it check.

So my compliance agent has this line, in capitals: never say you've sent an email without actually calling the tool. And the tool returns a confirmation with the message ID, so there's something concrete to report instead of a vibe.

It will also say it can't

The opposite failure shows up in the same agent. Ask it to send the company deck and it apologises: as an AI, it can't send emails. It has the tool. It has used the tool. But its training says assistants can't send email, and that wins unless you say otherwise. My sales agent's prompt has a whole section that starts: you must use these tools to take action; never say you cannot send emails.

Put those two rules side by side and the lesson is that the model's picture of what it can do is separate from what it can actually do. You have to keep telling it which is which.

A stub is a lie it will repeat

Early in a build, some tools are stubs: "schedule a demo" logs the request and returns "Demo scheduled." The agent will pass that straight on and tell the customer their demo is booked, when nothing is. If a tool isn't real yet, its return value has to say so, in words the agent will repeat.

Read back before writing

Before the agent saves anything, it reads back one sentence and waits: "Priya at Northwind, two hundred units a month, wants pricing by Friday. Save as new?" One sentence, not a form. On a voice call the read-back is the only screen the user gets. It also catches speech-to-text mistakes before they end up in the CRM. For bigger actions, like opening a dispute or emailing a supplier, the rule is blunter: always ask before creating cases or sending notifications.

Append, don't overwrite

When the agent updates a record, it never replaces the notes field. It adds a date-stamped paragraph to the end. A person's notes are worth more than anything the agent will write, and an agent that overwrites them once loses the sales team's trust for good. It's also the cheapest audit log you'll ever build.

Some things shouldn't be said out loud

On a call there may be other people in the room. My compliance agent knows pricing tiers and rebate percentages, and it won't say them out loud. It offers to send them securely instead. A supplier only ever hears about their own data, whoever is asking. Text-channel rules don't carry over to voice without thinking about who else can hear.

Voice has its own problems

Two settings matter more than the model choice. Start generating the reply before the speaker has quite finished, because people hear a half-second gap as the agent not listening. And when a cough or a door slam registers as an interruption and the agent stops mid-sentence, have it pick up again instead of waiting in silence. Both are a line of configuration in LiveKit, and both matter more than they look.

The pattern

None of these rules is clever. Each one closes the gap between what the model says and what the system did. A demo agent can get by on the model's fluency. An agent people let near their CRM needs every sentence it says about the world to be backed by a tool call that actually happened.
